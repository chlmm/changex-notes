# 性能分析与诊断

## 诊断策略总览

```
你遇到了什么问题？
├─ 程序跑得慢 ──→ CPU Profiler
├─ 内存占用异常 ──→ 内存分析
├─ 怀疑有内存泄漏 ──→ 内存分析 + CRT 调试堆
├─ 想提前发现潜在 bug ──→ 代码分析 (/analyze)
└─ 程序崩溃但没有明显报错 ──→ 调试（见 debugging.md）
```

## CPU 性能分析

### 使用 CPU Profiler

**入口**：调试 → 性能探查器 (Alt+F2)

**流程**：

```
1. 打开性能探查器
2. 选择分析目标（启动项目 / 附加到进程 / 已运行的程序）
3. 勾选 "CPU 使用率"
4. 点击开始
5. 操作程序复现性能问题
6. 停止收集
7. 分析结果
```

### 分析报告解读

#### 热路径 (Hot Path)

报告中最重要的一部分，显示消耗 CPU 时间最多的调用链。

```
看热路径的思路：
1. 找到最耗时的函数（顶部几个）
2. 看是谁调用了它（调用链上游）
3. 判断是：
   ├── 函数本身慢 ──→ 优化算法/实现
   ├── 被调用太多次 ──→ 减少调用次数/加缓存
   └── 调用链中的某个中间层浪费 ──→ 简化调用路径
```

#### 调用树 (Call Tree)

展开查看每个函数的时间分布，包括：
- **总时间 (Inclusive)**：包括子函数调用的时间
- **自身时间 (Exclusive)**：不包括子函数的时间

**关键**：自身时间高的函数才是真正需要优化的。总时间高但自身时间低说明瓶颈在子函数。

#### 函数详情

双击函数可查看源码级别的耗时标注，哪一行花了多少时间一目了然。

### 采样 vs 检测

| 模式 | 原理 | 开销 | 精度 | 适合 |
|------|------|------|------|------|
| 采样 (Sampling) | 定期中断记录调用栈 | 低 | 粗略 | 快速定位热点 |
| 检测 (Instrumentation) | 在函数入口/出口插桩 | 高 | 精确 | 精确测量特定函数 |

**建议**：先用采样找热点，再用检测精确测量。

## 内存分析

### 使用内存使用率工具

**入口**：调试 → 性能探查器 → 内存使用率

**流程**：

```
1. 启动内存分析
2. 操作程序到稳定状态
3. 拍摄快照 A
4. 执行可能泄漏的操作
5. 拍摄快照 B
6. 对比两个快照的差异
```

### 快照对比分析

对比两个快照时，关注：

| 指标 | 含义 | 怎么看 |
|------|------|--------|
| 对象增量 | 两个快照间新增的对象 | 正值可能有泄漏 |
| 堆大小增量 | 两个快照间堆内存增长 | 持续增长说明泄漏 |
| 对象类型 | 哪种类型的对象增加了 | 帮你定位到具体类 |

### 内存泄漏定位

```
1. 快照对比 → 找到持续增长的对象类型
2. 查看该类型的引用链 → 谁持有这些对象
3. 检查持有者是否有正确的释放逻辑
4. 如果是原始指针 → 考虑换用智能指针
```

### CRT 调试堆

C++ 程序检测内存泄漏的经典方法：

```cpp
// 在 main.cpp 开头
#define _CRTDBG_MAP_ALLOC
#include <cstdlib>
#include <crtdbg.h>

// 在 main() 末尾
_CrtDumpMemoryLeaks();
```

**输出**：如果有泄漏，会在输出窗口显示泄漏的内存块编号和分配位置。

**更精确的检测**：

```cpp
// 在 main() 开头设置检查点
_CrtMemState s1, s2, s3;
_CrtMemCheckpoint(&s1);

// ... 执行要检测的代码 ...

_CrtMemCheckpoint(&s2);

// 对比
if (_CrtMemDifference(&s3, &s1, &s2)) {
    _CrtMemDumpStatistics(&s3);
}
```

## 代码分析 (/analyze)

### 启用方式

属性 → C/C++ → 常规 → 启用代码分析 → 是

或：分析 → 对解决方案运行代码分析

### 常见警告类别

| 警告范围 | 典型问题 | 严重性 |
|----------|---------|--------|
| C6001 | 使用未初始化的变量 | 高 |
| C6011 | 解引用空指针 | 高 |
| C6201 | 数组越界 | 高 |
| C6308 | 内存泄漏（realloc 后未释放旧指针） | 高 |
| C6385 | 缓冲区溢出 | 高 |
| C26800 | 使用已移动的对象 | 中 |
| C26451 | 算术溢出 | 中 |

### 策略

```
代码分析结果怎么处理？
├─ 高置信度的警告 ──→ 立即修复
├─ 误报（确实安全的代码）───→ 用 _Analysis_assume_ 或 #pragma warning suppress 标注
├─ 不确定是否误报 ──→ 仔细分析，宁可修也不放过
└─ 低优先级警告 ──→ 记录到 TODO，不要阻塞当前工作
```

## 性能优化策略树

### 优化前先确认瓶颈

```
程序慢
├─ CPU 满载？ ──→ CPU Profiler 找热点
├─ 内存不够？ ──→ 内存分析 查泄漏/峰值
├─ I/O 等待？ ──→ 检查文件/网络操作
└─ 不确定？ ──→ CPU Profiler 先跑一遍
```

### 常见优化手段

| 瓶颈类型 | 优化方向 | 常见手段 |
|----------|---------|---------|
| 算法瓶颈 | 换算法 | O(n²) → O(n log n)，哈希替代线性查找 |
| 内存瓶颈 | 减少分配 | 对象池、预分配、避免频繁 new/delete |
| 缓存不友好 | 改数据布局 | SoA 代替 AoS、连续内存、减少指针追逐 |
| 编译优化 | 编译器选项 | `/O2`、`/GL`（全程序优化）、`/LTCG`（链接时代码生成） |
| 并行化 | 多线程 | OpenMP、std::async、线程池 |

### 优化检查清单

- [ ] 先 Profile，不要猜
- [ ] 一次只改一个变量
- [ ] 改完再 Profile 对比
- [ ] 不以"看起来快了"为依据，以数据为依据
- [ ] 关注 Release 配置的性能（Debug 的性能数据无意义）

## 常见问题

### 问题：Profiler 附加后程序变慢

**原因**：分析本身有开销，特别是检测模式。

**解决**：
- 用采样模式代替检测模式
- 缩短分析时间窗口（只录制问题发生的那段时间）
- 减少同时启用的分析器数量

### 问题：代码分析误报太多

**解决**：
- 在项目属性中配置规则集，只启用关心的规则
- 用 `[[suppress("警告号")]]` 或 `#pragma warning(disable: 警告号)` 抑制特定误报
- 升级 VS 版本，新版的分析器误报更少
